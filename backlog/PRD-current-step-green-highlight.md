# PRD: Current Step Geometry Green Highlight

## Problem Statement

As a user stepping through geometric constructions in the SG Geometry application, I have no visual indication of which geometries were created in the current step. This makes it difficult to understand the construction progression and identify which step's output I am currently viewing. Without this feedback, the step-by-step exploration experience is confusing and less educational.

## Solution

Implement visual highlighting that renders geometries created in the current step in green (#00ff00). The highlight appears when a user navigates to a step and persists until they move to the next or previous step. This provides immediate, clear visual feedback about which step's geometries are being displayed.

The solution uses a **renderer-based approach** where step IDs are generated by DSL expressions, passed to the renderer during drawing, and the renderer applies the green color when the step ID matches the current step. This approach cleanly separates computation logic from rendering logic and avoids fragile DOM manipulation.

## User Stories

### Core Visual Feedback

1. As a geometry construction viewer, I want geometries created in the current step to appear in green, so that I can visually identify which step's output I am viewing
2. As a geometry construction viewer, I want the green highlight to appear immediately when I click next/previous step, so that I get instant feedback on my action
3. As a geometry construction viewer, I want the green highlight to persist on the current step's geometries until I navigate away, so that I have time to study the construction
4. As a geometry construction viewer, I want all geometry types (point, line, circle, polygon, coordinate_system) to be highlightable in green, so that every type of construction output is clearly indicated

### Done State Behavior

5. As a geometry construction viewer, I want no green highlight when I am at step 0 (before any steps), so that the initial empty state is clear
6. As a geometry construction viewer, I want no green highlight when I have completed all steps (currentStep > totalSteps), so that I know the construction is finished
7. As a geometry construction viewer, I want the final construction to display only outline colors (no green) when complete, so that I can see the finished result without step highlighting

### Color Precedence

8. As a geometry construction viewer, I want selected geometries to appear in red even when they are in the current step, so that my explicit selection takes precedence over step highlighting
9. As a geometry construction viewer, I want input-highlighted geometries (inputs to selected geometry) to appear in orange when not selected, so that dependency relationships are visible
10. As a geometry construction viewer, I want the color precedence to be selection (red) > input highlight (orange) > current step (green), so that the most important visual feedback always wins

### Coordinate System Specifics

11. As a geometry construction viewer, I want coordinate system arrows to be highlighted in green when created in the current step, so that the reference frame is clearly indicated
12. As a geometry construction viewer, I want coordinate system arrowhead markers to also be green when the coordinate system is highlighted, so that the visual indication is complete

### Construction Isolation

13. As a geometry construction viewer, I want each construction type (square, sixfold, sixfold-v1) to have isolated step highlighting, so that viewing one construction doesn't affect others
14. As a geometry construction viewer, I want to be able to step through multiple constructions independently, so that each maintains its own current step state

### DSL Construction Specifics

15. As a DSL construction viewer, I want Square DSL construction to show green highlight for current step geometries, so that the declarative square construction is fully featured
16. As a DSL construction viewer, I want SixFold V0 DSL construction to show green highlight for current step geometries, so that the sixfold pattern construction is fully featured
17. As a DSL construction viewer, I want SixFold V1 DSL construction to show green highlight for current step geometries, so that the advanced sixfold construction is fully featured

### Quality & Reliability

18. As a geometry construction viewer, I want the highlight to work consistently across all browsers, so that my experience is reliable
19. As a geometry construction viewer, I want the highlight to not cause any visual glitches or flickering, so that the experience is smooth
20. As a geometry construction viewer, I want the existing visual output (colors, styles) to remain unchanged except for the green highlight, so that I don't lose familiar visual cues

## Implementation Decisions

### Architecture

- **Renderer Pattern with Dependency Injection**: The solution uses a `GeometryRenderer` interface that separates expression computation from SVG rendering. Expressions define what to compute; renderers define how to draw it. This maintains clean separation of concerns and makes both easier to test and modify independently.

- **Step ID Generation via Expressions**: Each DSL expression's `compile()` method generates a unique step ID from its ID using `createStepId(namespace, id)`. The step ID is passed to the renderer during the `draw()` call, allowing the renderer to apply highlighting when the step ID matches the current step.

- **Current Step Tracking**: The `DefaultGeometryRenderer` maintains a `currentStepId` state. When `stepId === currentStepId` during drawing, the geometry is rendered with `COLOR_CURRENT_STEP` (#00ff00).

### Step ID Namespacing

- **Namespace by Construction**: To prevent ID collisions across different DSL constructions (all use "cs" for coordinate system), step IDs are namespaced by construction type. The format is `step_<namespace>.<id>` (e.g., `step_square.cs`, `step_sixfold.cs`, `step_sixfold-v1.cs`).

- **Mandatory Namespace**: Namespace is a required parameter with no default. This is enforced at runtime - `createStepId()` throws an error if namespace is empty or undefined.

- **Namespace Propagation**: Namespace flows through the system as follows:
  - Construction functions (`buildSquareDslSteps`, etc.) receive namespace as a parameter
  - Namespace is passed to the `DefaultGeometryRenderer` constructor
  - Renderer stores namespace and exposes it via `renderer.namespace`
  - Expressions access namespace via `renderer.namespace` in their `compile()` method

### Modules to Modify

**Renderer Module**
- Interface: `GeometryRenderer` gains `namespace: string` property
- Implementation: `DefaultGeometryRenderer` stores and exposes namespace, uses it for step ID matching
- Responsibility: Apply color highlighting during draw when step ID matches current step ID

**Step ID Utility Module**
- Function: `createStepId(namespace: string, id: string): string`
- Behavior: Returns `step_<namespace>.<id>`, throws on empty namespace
- Responsibility: Centralized step ID generation with collision prevention

**DSL Expression Module**
- All expression classes: Modify `compile()` to use `createStepId(renderer.namespace, this.id)`
- Responsibility: Generate namespaced step IDs during compilation

**DSL Construction Module**
- Construction functions: Add `namespace: string` parameter
- Responsibility: Provide namespace to builder and renderer

**DSL SVG Component Module**
- Components: Pass construction-specific namespace to build functions
- Responsibility: Initiate construction with correct namespace

**Theme Module**
- Already complete: `COLOR_CURRENT_STEP: string` added to `Theme` interface
- Values: `#00ff00` (pure green) for both light and dark themes

### Geometry Type Handling

- **Point**: Fill color set to `COLOR_CURRENT_STEP`
- **Line**: Stroke color set to `COLOR_CURRENT_STEP`
- **Circle**: Stroke color set to `COLOR_CURRENT_STEP`
- **Polygon**: Stroke color set to `COLOR_CURRENT_STEP`
- **Coordinate System**: Stroke color on arrows and arrowhead marker fill set to `COLOR_CURRENT_STEP`

### Done State Handling

- **Boundary Conditions**: `currentStepId` is set to empty string when `currentStep <= 0` or `currentStep >= allSteps.length`
- **Effect**: No geometries receive green highlighting in done state
- **Final Construction**: Shows only theme default colors (no green)

### Arrowhead Marker Handling

- **Mechanism**: `strokeColor` parameter passed through from renderer to `svgDrawCoordinateSystem` to `coordinateSystemArrows` to `ensureArrowheadMarker`
- **Result**: Arrowhead markers automatically inherit the current step color when coordinate system is highlighted
- **No DOM Queries**: Avoids fragile `querySelector` approaches; color is set during element creation

### Scope Limitation

- **DSL-Only**: Current step highlighting is intentionally limited to DSL-based components (`SquareDslSvg`, `SixFoldDslSvg`, `SixFoldDslV1Svg`)
- **Legacy Exclusion**: Non-DSL components (`SquareSvg`, `SixFoldV0Svg`, `RotatedSquareSvg`) do not receive highlighting
- **Rationale**: DSL components represent the future architecture; legacy components will be migrated or deprecated

## Testing Decisions

### Test Philosophy

Tests should verify external behavior, not implementation details. Focus on: does the geometry appear in green when it should, and not green when it shouldn't?

### Modules to Test

**Unit Tests - Renderer Logic**
- Module: `DefaultGeometryRenderer`
- Coverage: All `drawXXX()` methods with matching and non-matching step IDs
- Geometry types: Point, line, circle, polygon, coordinate system
- States: Normal, current step, done state
- Prior art: Existing `defaultRenderer.test.ts` with 36 tests covering type validation and highlighting

**Integration Tests - Component Behavior**
- Module: DSL SVG components (`SquareDslSvg`, `SixFoldDslSvg`, `SixFoldDslV1Svg`)
- Coverage: Step navigation, highlight application, done state
- Approach: React Testing Library in jsdom environment
- Verification: Query rendered SVG for elements with `fill="#00ff00"` or `stroke="#00ff00"`

**Integration Tests - Precedence Chain**
- Module: Interaction between selection, input highlight, and current step
- Coverage: Selection (red) overrides current step (green), input highlight (orange) overrides current step (green)
- Approach: React Testing Library with user interaction simulation

### Test Cases by Geometry Type

For each geometry type (point, line, circle, polygon, coordinate_system):
1. Geometry with matching step ID renders with `COLOR_CURRENT_STEP`
2. Geometry with non-matching step ID renders with default colors
3. Geometry with matching step ID but selected renders with `COLOR_SELECTED` (red wins)
4. Geometry with matching step ID but input-highlighted renders with `COLOR_INPUT_HIGHLIGHT` (orange wins)

### Done State Test Cases

1. `currentStep = 0` → No geometries highlighted
2. `currentStep = 1` → Step 0 geometries highlighted
3. `currentStep = N` (where N = totalSteps) → Step N-1 geometries highlighted
4. `currentStep = N+1` → No geometries highlighted (done state)

## Out of Scope

- **Non-DSL Components**: `SquareSvg`, `SixFoldV0Svg`, `RotatedSquareSvg` will not receive current step highlighting in this implementation
- **Post-draw Approach**: The alternative post-draw highlighting approach (iterating store after rendering) is not being implemented
- **Animation**: No animation or transition effects for highlight appearance/disappearance
- **Customization**: No UI controls for changing the highlight color (it's always green #00ff00)
- **Persistence**: No saving/loading of current step state
- **URL Sharing**: No URL parameters for current step
- **Keyboard Navigation**: No keyboard shortcuts for stepping (only click-based)
